tinyactor 来碰瓷 Go 啦！关于性能的误区

2026-11-14

写完 tinyactor 这个项目之后，我基本上再没碰过我手写的 cora 项目。 它们都服务于同一个梦想，就是用我自己设计的语言来写东西。cora 是我许多年的思考和探索，是一行一行手敲出来的心血的结晶，并且，它是 lisp！ 但是 tinyactor 不是，我没有手写一行的代码，全是让 agent 写的。而且 tinyactor 也不是 lisp 语法，理由是我发现 agent 写代码不喜欢 lisp 中 ))))))) 这样地狱级的括号对齐，容易犯错。

tinyactor 并没有像 cora 那样，选择编译到 C，而是用性能更差的 bytecode VM 方式。 为什么呢？VM 并不是慢到没法用，而是通用性更好。关于性能，大众有不少误解。 所以本文就是聊一聊关于性能的误区，并且特定场景下 tinyactor 甚至不比 Go 慢，哪怕它是用 VM 实现。

第一个故事：栈虚拟机真的比寄存器虚拟机慢么？

解释器实现，一般有 AST 树遍历的解释器，以及编译成字节码的解释器。前者性能太差了，很少有实际的生产场景中使用，而后者则能用于通用场景。 字节码解释器又可以细分于基于栈虚拟机，和基于寄存器虚拟机。

lua 就是寄存器虚拟机，大众通常会觉得寄存器虚拟机更快一些，觉得 lua 是最快的解释器之一，是因为它是寄存器虚拟机。 这其实是一个误解！经过一些优化的栈虚拟机，其实速度并不落后于寄存器虚拟机。

我们先看看，常规的栈虚拟机实现，性能为什么容易落后于寄存器虚拟机。

以 (+ a b) 这个表达式为例，编译到栈虚拟机的字节码，一般是

load i
push
load j
push
add

而编译到寄存器虚拟机的字节码，则一般是

R[i] = R[i] + R[j]

也就是说，寄存器虚拟机的指令数，往往比栈虚拟机的指令数短很多！ 指令数为什么会影响到性能呢？这就不得不说一个解释器的解释开销。

字节码解释器的写法大概可理解为这样的伪代码：

while (1) {
    opcode = bytecode[ip]
    switch (opcode) {
        case PUSH: ...
        case ADD:  ...
    }
}

它就涉及取出一条指令，根据指令做 switch，跳进去，再跳回 for 循环做下一条指令派发。 相对于 push / pop / add 这些实际执行的事情，opcode 消耗在 dispatch loop 的开销是很大的。 指令数越多，这块浪费的总体开销就越大。

寄存器虚拟机相比于栈虚拟机，指令数量更短，同样的程序编译出来，它的 dispatch 上的开销就会节省很多。 不过没关系，stack 虚拟机虽然指令数更多，但是有一个技巧叫 superinstructions 可以把指令数省下来。

superinstructions

"超级指令"，就是我们可以观察和分析字节码里面，那些共同出来的 pattern，把多条指令合并成一条指令。

比如说这里

load, push 取一个局部变量，把它放到栈顶，这两条指令经常是成对出现的，我们可以把它缩写成一个 loadp 指令，表示 load + push。 类似的还有 constp, globp，都是常量、全局变量加上 push 的复合指令。

然后还有 JIF_LT，这个是 jump if less than，因为我们频繁会出现比较，比完之后根据结果立马再 jump。原始的 op_lt 和 op_jif 就可以合并成 op_jif_lt。

当我们把这些常见的指令组合，变成单条超级指令之后，我测试过一个实际数据，同样一个真实程序，字节码的指令数大约减少了 30~40%。 这个优化之后，我们就可以把栈虚拟机的指令数多于寄存器虚拟机的劣势，追回一大部分了。

这个优化也很容易做，就是拿一些实际的程序的指令分析一下，哪些是经常一起出来的。 然后生成代码那边改一改，发射指令的时候，如果前一条指令跟后一条指令正好符合可组合的 pattern，就合并掉。

top-of-stack-caching

再说另一个栈虚拟机和寄存器虚拟机的差异点。寄存器虚拟机这边，它的计算的落点是不受位置的限制的，就是说你可以使用最后面的位置，也可以使用中间任意位置。

比如说代码是

(let (a  42)
    ...
    (+ a 3))

假设一个变量 a 在位置为 3 的 slot。假设当前 pos 是 18。 在寄存器虚拟机这边，它完全是可以这样操作的

R[18] = R[18] + R[3]

就是说可以任意位置寻址。但是栈虚拟机不一样，不能是任意位置，它只能在栈顶位置操作。 也就是

load 3
push
add

先从 slot 3 位置把变量 a 捞到栈顶，然后才能对栈顶的两数加 add 操作。 这个需要 push 到栈顶后，才能参与计算的过程，也是一个栈虚拟机相对于寄存器虚拟机的劣势。

但是...这种也是可以做优化的。

其实所谓的寄存器虚拟机，它只是一个内存中的表示。一般是用一个 R[] 这样的数组。 在 C 代码里面，是 R[i] R[j] R[k] 这些东西来搞的虚拟寄存器。 这意味着，它们并不能真正使用到物理硬件寄存器！

栈虚拟机这边，我们一般是用的 base[sp] 来搞的栈。两者其实都不能用到物理的寄存器。 但是当我们写 C 代码的时候，我们可以用一些技巧，让 C 语言的局部变量来充当物理的寄存器。

代码不能写成这样（伪代码）：

struct VM {
    Obj base[];
    Obj val;
    int ip;
    int sp;
}

void run(struct VM *vm) {
    while (1) {
        switch (op) {
        case op_load:
            vm->val = vm->base[i];
        case op_push:
            vm->val = vm->base[vm->sp++];
        }
    }
}

这样写全部是基于 vm 做间接访问的，对物理寄存器的利用特别差！

我们需要这样写：

void run(struct VM *vm) {
    Obj val = vm->val;
    Obj *sp = &vm->base[vm->sp];

    while (1) {
       switch (op) {
        case op_load:
            val = bp[i];
        case op_push:
            *sp++ = val;
        }
    }

    vm->sp = sp - vm->base;
    vm->val = val;
}

注意到差异是什么？我们在进入 run 的时候，先把这些值读进 C 函数的局部变量， 直到退出 run 再把局部变量刷回 vm 中，中间的代码都不是通过 vm 做间接访问的。 这么写代码，局部变量会被分配真实的物理寄存器，效率远高于 vm->xx 间接访问。

那 top-of-stack-caching 又是一个什么样的技巧呢？我们可以假设永远有一个寄存器，作为栈顶位置。 假设没有 top-of-stack 寄存器的时候，我们做

(+ a b)

是需要

push a
push b
add

而有了这个虚拟的寄存器之后，我们实际上是这样发的字节码：

loadp a    ; load + push 一条搞定，a 进栈
load  b    ; b 直接落进 val，不压栈
add        ; val = val + 弹栈

看到没，原来 5 条指令（load/push/load/push/add），现在 3 条，并且第二次的 push 省掉了！还有，由于 val 是 C 的局部变量，它是会被映射成物理寄存器的！

而寄存器虚拟机，R[i] = R[i] + R[j]，这个 R[n] 的访问并不是走物理寄存器，而是走的内存。

你肯定想问，难道寄存器虚拟机，就不能直接写成 Ri Rj Rk ... 这样的 C 语言局部变量，从而利用真正的物理寄存器么？

不能。因为进入 dispatch 之后，把字段赋值到 C 局部变量，再到 dispatch 返回的时候把 C 局部变量刷回去， 这个套路的前提是参与运算的东西只有 val 一个（栈虚拟机的 top-of-stack-caching 正好满足）。 而寄存器虚拟机，R[n] 的槽位是很多的，就没法做这种「进入时复制到 C 变量，退出时再刷回 vm」的操作了。

经过 superinstructions / top-of-stack-caching 等这些优化之后，栈虚拟机的效率，其实并不弱于寄存器虚拟机。

我实测比较过 tinyactor 跟 python lua php 这些主流的，还有包括 wren janet petite 等等这些小众的，VM 实现的性能。 其实结果都算是在同一梯队。

凭印象，大家觉得最快和最慢的分别是哪个？打破偏见，php 并不是最慢的，而且还处于中上水平。 python 经过最近的几个版本的优化，进步不小，但是还是要落后于 tinyactor 一些。 wren 是 crafting interpreters 的作者写的一门语言，大家肯定会觉得，这是由解释器专家写出来的嘛，肯定性能比 tinyactor 会更好一些。 但是打破偏见，真正的结果是，它也是总体略弱于 tinyactor 一点的。

最快的是 petite，这是 chez scheme 的解释器版本。但 tinyactor 咬得很紧，差个 10%，具体要看 case。 传说中它可以以解释器身份去碰瓷编译器的性能的，实际验证下来，并不能。也就是性能比较好的解释器罢了。 任何带 jit 或者 aot 的编译的，如果在数值计算这个方向不能至少 3 倍以上吊打解释器实现的，那作者一定是脑子不太够用，不建议当程序员。

把上面这些印象落成数字。case 从这里那一套里挑三个：递归的 fib(32)、tak(26,18,9)、还有一个 1600 万次的循环累加。每个跑三遍取最快，全部归一到 tinyactor = 1.00，数越小越快：

| 实现 | fib(32) | tak | 循环累加 | 几何平均 | |---|---|---|---|---| | tinyactor（预编译 .tabc） | 1.00 | 1.00 | 1.00 | 1.00 | | lua 5.5（寄存器 VM） | 0.92 | 0.95 | 0.65 | 0.82 | | petite（chez 的解释器） | 0.89 | 0.96 | 1.04 | 0.96 | | janet | 0.95 | 0.88 | 1.48 | 1.08 | | python 3.15 | 1.41 | 1.17 | 1.57 | 1.37 | | guile 3.0 | 3.47 | 3.47 | 5.34 | 4.00 | | luajit（JIT） | 0.20 | 0.17 | 0.14 | 0.17 | | chez（编译执行） | 0.47 | 0.39 | 0.24 | 0.35 |

看这张表：lua 两个 case 跟 tinyactor 打平，循环累加上反过来比我快 35%；petite 一个赢一个平一个略输；janet 是循环快、递归输。这就是「同一梯队」具体长什么样——纯解释器这一堆里，谁也没跟谁拉开一倍。

从前，做这些对比会比较麻烦，因为不好掌握那么多种语言去写一些 benchmark。 但是现在有 agent 了很容易的，就一句话的事，让它把 case 弄过来，对比一下 A B C D ... 这些语言的性能。

第二个故事：tinyactor vs Go, tinyactor 有资格碰瓷么？

前面已经说过了，tinyactor 就是一个基于栈虚拟机的字节码解释器实现，而 Go 语言是编译型的呀，tinyactor 怎么可能碰瓷呢？

先来一个开胃小菜。

Go 是用 goroutine 支持并发的，tinyactor 是一个 actor 模型。

我们来一个 1M actor 的测试，对比内存开销。tinyactor 的：

fn worker() {
    recv()
}

fn spawn_workers(n) {
    if n == 0 {
        print("READY")
        recv()
    } else {
        spawn(fn { worker() })
        spawn_workers(n - 1)
    }
}

fn main() {
    spawn_workers(1000000)
}

Go 的：

func main() {
    ch := make(chan struct{})
    for i:=0; i<1000000; i++ {
        go func() {
            <-ch
        }
    }
    fmt.Println("READY")
    time.Sleep(time.Hour)
    close(ch)
}

两个都是启动完就卡住不返回的，等它打出 READY，用 vmmap -summary 量一下物理内存（physical footprint）：

| | tinyactor | go | |---|---|---| | 1M 个躺着不干活的进程 / goroutine | 998 MB | 2.6 GB | | 平摊到每一个 | <1.0 KB | ~2.6 KB |

2.6 倍。差在哪？Go 的 goroutine 一起来就先给 2KB 栈，加上 g 结构体本身的开销；tinyactor 的进程只有一个 Proc 头，栈是所有进程共用一根值栈，阻塞的进程在上面就占自己那一帧，几个槽的事。

如果让 tinyactor 写的 fib(30) 跟 Go 的实现比，那肯定是被吊着打的。但是可以“作弊”，tinyactor 可以把模块用 C 实现，让 C 去跟 Go 拼刺刀，而 tinyactor 留着当粘合剂。

不能用这么明显的方式去碰瓷，显得底气不足。我构造的场景是这样的。

写了一个两边都能跑的 HTTP 服务——TA 一份，Go 一份——然后用同一个压测客户端压它们。为了让比较不变成「谁写的 HTTP 解析器更聪明」，服务被设计得很窄：读请求头、算一个 SHA-256、写一行 JSON。

POST /light     (no body)   →   {"bytes":65536,"sha256":"<hex>"}
POST /heavy     (no body)   →   {"bytes":16777216,"sha256":"<hex>"}
POST /delay1ms  (no body)   →   {"delay_ms":1}
POST /fairness  (no body)   →   {"counts":[c0,...,c31]}

四个端点，四种工作：

  • /light：64KB 摘要。绝大多数真实服务的样子——请求小、计算小，但请求路径本身有开销。
  • /heavy：16MB 摘要。CPU 密集，是「用 C 算重活」的典型场景。
  • /delay1ms：睡 1ms 再答。延迟敏感请求——它测的是运行时把挂起的 actor 叫醒要多久。
  • /fairness：32 个 CPU-bound worker 跑 3s，回传各自的迭代次数。公平性实验——服务只管干活，离散度由客户端算。

工作量是协议的一部分（大小固定在端点里，不是请求体里），负载形态由客户端决定：客户端只负责挑端点（HEAVYPCT 是 /heavy 的占比，DELAYC 是同时跑的延迟敏感探针条数，-fairness 是跑公平性实验），两侧拿到完全相同的端点序列。

这件事是这次重做基准的核心。上一版的协议是 POST /digest {"bytes":N}，大小跟着请求走——那意味着「工作量」是请求的一部分，客户端的 body 解析开销、两侧 body 是否真的一致，都要额外校验。现在负载是协议的一部分，两侧做的工作逐字节相同，runner 每次跑都抽检两边的响应摘要（same work: yes / digest: every sampled response matched）。

角度一：语言 —— 调 C 内核，TA 不比 Go 慢

先看最干净的一组数：单客户端、无排队，纯粹测每请求的成本。

| | tinyactor | go | ta/go | |---|---|---|---| | light 请求（64KB 摘要） | 0.112 ms | 0.052 ms | 2.15× | | heavy 请求（16MB 摘要） | 6.091 ms | 6.052 ms | 1.01× | | light req/s | 8435/s | 18553/s | 0.45× | | heavy req/s | 163/s | 158/s | 1.03× |

heavy 是打平的：16MB 摘要 6.091ms 对 6.052ms，吞吐 163/s 对 158/s。

怎么验证「打平」不是因为两边都没认真干活？把两组数相减：16MB 减去 64KB 的那部分摘要，TA 花 5.98ms，Go 花 6.00ms——两侧的 SHA-256 都是 ~2.7 GB/s。内核那层两边一模一样。

再把 light 那一行拆开：64KB 摘要在 2.7 GB/s 下只要 0.023ms，可 TA 的 light 请求总共花了 0.112ms，Go 花了 0.052ms。扣掉内核，TA 的请求路径 0.089ms，Go 0.029ms。

所以 2.15× 全部来自请求路径：HTTP 头解析、JSON、actor 分发。这是 TA 要还的债，但跟 C 没关系。

一句话：在 TA 里用 C 算重活，重活本身不吃亏（1.01×）；TA 比 Go 慢的地方是胶水，不是内核。

角度二：延迟 —— 尾延迟是调度器的指纹

延迟这块我看两件事：调度器公不公平，还有 CPU 打满的时候，等着的小请求、和刚睡醒的 actor，各自要等多久。

公平性

公平性也是同一个服务的一个端点（POST /fairness），不是另写一份程序：服务里 32 个 actor 跑 3s，回传各自的迭代次数，客户端算离散度——所以两侧被测的是同一件事。

先把「公平」这件事单独测干净：32 个 CPU-bound actor，各跑 3 秒，谁也不主动让路，只能靠运行时抢占。看迭代次数的离散度 dev = (max-min)/max × 100000，越小越公平。

| workers | tinyactor dev | go dev | ta/go | |---|---|---|---| | 1 | 14 | 33007 | 2358× | | 2 | 7 | 21659 | 3094× | | 4 | 69 | 35147 | 509× | | 8 | 4997 | 35105 | 7.0× |

单 worker 就能看出 Go 的调度器有多粗：32 个 actor 抢一个核，Go 那边最忙的 actor 比最闲的多跑了 33007/100000（33%），TA 那边是 14/100000（0.014%）。差三个数量级。

（8 worker 那行噪声大：32 个 actor 摊到 8 个 worker 上，而这台机器是 4 个性能核 + 4 个能效核，actor 落在哪个核上直接决定离散度。3 次重复里 TA 那边在 4163–4997 之间晃，Go 那边在 28005–35105 之间晃。）

CPU 满载下的尾延迟

现在回到 HTTP 服务：80/20 的摘要负载把 CPU 打满，同时打延迟敏感探针。6 worker 每侧：

| | tinyactor | go | ta/go | |---|---|---|---| | delay p50 | 2.33 | 8.94 | 0.26× | | delay p99 | 6.15 | 25.27 | 0.24× | | light p50 | 2.38 | 1.07 | 2.22× | | light p99 | 6.33 | 14.33 | 0.44× | | heavy p50 | 12.02 | 8.79 | 1.37× | | heavy p99 | 18.00 | 22.98 | 0.78× |

三件事：

1. 唤醒延迟差 4 倍。 /delay1ms 只睡 1ms，客户端看到 2.33ms（TA）对 8.94ms（Go）。多出来的 8ms 是 Go 的 runtime 让醒来的 goroutine 排在 CPU-bound 后面等一个 10ms 的时间片。TA 这边是 FIFO 队列 + 1000 reduction 的片预算，醒来的 actor 最多等前面几个 actor 各跑一个片。单 worker 时更明显：8.69ms 对 28.63ms（0.30×），p99 16.99 对 66.92（0.25×）。 2. 加到 8 个 P 也不能救。 8 worker 时 Go 的 delay p50 还是 7.70ms（TA 1.98ms，0.26×）——Go 的 goroutine 醒来后要排在 run queue 后面，而且当前的 CPU-bound goroutine 还要跑满它的时间片（Go 的抢占周期是 10ms）才会被换下来；加 P 改变不了这件事。TA 这边是另一套机制：调度器是 FIFO 运行队列 + 固定 reduction 预算（1000，scheduler.c 里的 MAX_REDUCTIONS），一个 actor 跑完一个片就重新入队到队尾，所以醒来的 actor 最多等「排在它前面那几个」各跑一个片。一个片大约 0.9ms（16MB 摘要一次请求让出 7 次，6.091ms / 7），醒来的 actor 前面平均排了两三个，p50 2.33ms 这个量级对得上。 3. 小请求的尾巴被 heavy 拖着走，TA 拖着少得多。 这是「light 受到 heavy 影响小」的量化：CPU 满载时，Go 的 light p99 是 14.33ms，TA 是 6.33ms（0.44×）。heavy 请求在 Go 那边把整个核占满，小请求排在后面；TA 的时间片更粗但切换更有规律，小请求不会被无限期推后。

代价写在明处：p50 是反过来——TA 的 light p50 2.38ms 对 Go 的 1.07ms，慢 2.2×。切片粗，小请求偶尔要等当前时间片跑完。TA 换来的不是「都更快」，是尾巴更短、中位数更长。这个分布形状差异，是两种调度策略的直接投影。 （无探针的纯摘要负载下形状一样：light p50 2.12× 差、p99 0.42× 好；heavy p50 1.30× 差、p99 0.69× 好。）

角度三：吞吐 —— 有请求要等的服务，TA 多干 21%

前面两组都是单看一个指标。真实的服务不是这样，它是混的：一边有要烧 CPU 的重活，一边有要马上回的小请求，还有在等着的请求。这一角测的就是混起来的账。

先看纯摘要的 mix（6 worker，不带探针）：

| | tinyactor | go | ta/go | |---|---|---|---| | light req/s | 2974 | 3054 | 0.97× | | heavy req/s | 743 | 762 | 0.98× | | total req/s | 3717 | 3816 | 0.97× |

纯摘要的时候两边一个水平，总量差 3%，跟前面一致：重活是 C 在干，TA 不吃亏；TA 贵在胶水。

加上延迟敏感的探针（同样 6 worker，4 条探针），账就变了：

| | tinyactor | go | ta/go | |---|---|---|---| | delay req/s | 1596 | 396 | 4.03× | | light req/s | 2839 | 3077 | 0.92× | | heavy req/s | 710 | 767 | 0.93× | | total req/s | 5146 | 4240 | 1.21× |

总吞吐赢了 21%。

赢在哪儿？赢在探针：同样的延迟敏感负载，TA 多完成 4 倍（1596/s 对 396/s）。这 4 倍不是凭空来的——客户端是固定 4 条并发探针的闭环，吞吐 = 并发数 / 单请求延迟，上一节那个 4 倍的延迟差，直接就在这里变成 4 倍的吞吐差。

开始我以为 TA 是靠 light 多完成赢的，后来看数才发现不是（light 那一栏 TA 还少 8%）。真正的机制是：同样一台机器，一个调度器如果能把延迟敏感的请求照顾好，它手里的总时间就被更有效率地用了。Go 那边的 goroutine 醒来要排在 run queue 后面，还要等当前的 CPU-bound goroutine 跑满一个 10ms 时间片；这段时间那个核并没有在算它那份摘要，而是空转或者让给了一个抢不到优先级的请求。TA 是固定 reduction 预算，跑完一个片就重新排队，醒来的 actor 最多等前面几个各跑一个片。

所以这笔账是：TA 少做几个点的摘要，把探针多做四倍，净账 +21%。

这个故事的版本应该是：TA 不是「算得更快」，是「调度得更不浪费」。在一个「既有请求要等，又有 CPU 要烧」的服务里，后者才是总吞吐的来源——而真实的服务，基本都是这个形态。

一张表收一下

每项指标单独列出来：

| 角度 | 结论 | 关键数字（TA / Go） | |---|---|---| | 语言：调 C 内核 | 不吃亏 | heavy 16MB 摘要 6.091 / 6.052 ms（1.01×） | | 语言：请求路径 | 慢 2.15×，是下一笔债 | 扣内核后 0.089 / 0.029 ms | | 延迟：公平性 | 高三个数量级 | dev 14 / 33007（1 worker） | | 延迟：唤醒 | 快 4 倍 | delay p50 2.33 / 8.94 ms | | 延迟：小请求尾巴 | 短一半多 | light p99 6.33 / 14.33 ms | | 延迟：小请求中位数 | 慢 2.2×（代价） | light p50 2.38 / 1.07 ms | | 吞吐：纯摘要 | 打平 | total 3717 / 3816 req/s（0.97×） | | 吞吐：带延迟敏感负载 | 赢 21% | total 5146 / 4240 req/s（1.21×） |

那这么多数字里最关键的是哪几个？我自己只看这五条：

  • 计算密集的重查询：打平
  • 1m actor 的内存开销：tinyactor 赢
  • 调度公平性：tinyactor 赢
  • 混合负载总吞：tinyactor 赢
  • 混合负载轻查询的 P99 延迟：tinyactor 吊打 Go

第三个故事：编译到 C 性能就会更好么？

我曾经也无数次地摇摆 -- 会不会编译到 jit 性能就更好一些，亦或是生成到 C 可以取得一个性能和实现复杂性上的一个甜点区？

无论是 cora 还是 tinyactor，它们都是自己管理堆栈的，这是为了 GC 那边好处理，不依赖 C 的原生栈。 代价就是，如果翻译到 C 就不能够直接做 1:1 的翻译。因为一旦用 C 的栈之后，要支持非常多的 actor 上下文切换，就要去弄汇编层的奇技淫巧了，并且给 GC 带来特别多的麻烦。 而自己管理 vm 堆栈，并且无副作用语言，可以每个 vm 独立 GC。这些优势是我不想放弃的。

cora 翻译到 C 的做法我已经在另一篇博客中记录过，这里不重复。

tinyactor 编译到 C 的方式，我想了想，一种方式还是像 cora 这样做，它可以这样生成到 C，但是不用 coroutine 这个 feature，只是把堆栈管理暴露出来。 还有一种做法就是转换成寄存器虚拟机，然后栈都是基于 R[i] 这样子来搞，也是自己控制的堆栈。 后者我感觉可能还不如前者，毕竟 C 局部变量没被当成寄存器被充分利用上。

编译到 C 额外引入的复杂度还是高了不少的。所以真正做之前我定了一个指标给 agent：如果至少快 3 倍以上，这个把事就值得投入，否则不值得做。

用一些单元轻量测试验证之后，结果是 fib / collatz / tailcall 这些纯计算型的都能有 3 倍以上的收益。 而像 takl / map 这一类的带上 cons 分配的 case，则效果不明显。

于是我又想，换一个 case，就拿 tinyactor 的编译器自举过程来验证收益，这是一个接近真实场景的例子， 如果编译到 C 能够比虚拟机解释快，就值得做。这个测试结果验证下来，这是一个提升有 4X+ 的负载。

所以我决定继续做一做。等做出来之后，我又换了一个负载再测。 我还是拿那个 tinyactor vs go 的 case 去做验证，结果发现收益只有 1.1~1.2X。 这收益太小了，完全不值得。

让 agent 分析为什么，答案是这样的：压测过程中观察，只有 22% 的 CPU 时间是落在 tinyactor 内的，而其它过半的时间是在 C 模块实现的重型计算里面。 然后不管是 VM 还是 cgen，都共同有很大一块是在 malloc 和 GC 里面。所以这就导致，这个负载即使生成到 C，也是总体没有什么收效的。 可以优化的是做 runtime 层的优化，那个是 VM 和 cgen 两边都受益的。

看到这样的数据之后，我对编译到 C 方案就彻底去魅了，老老实实就用 VM 方式。 重计算的，可以用 C 去写模块，扬长避短。

回到"性能误区"这件事

三个故事讲完，其实想说的只有一件事：性能上的结论，脱离场景是没有意义的。

我们的大脑太容易陷进这种误区里：VM 就是慢的，编译到 C 就是快的，goroutine 就是轻的，lisp 就是慢的，某某语言就是比另一个快。这往往都不成立——它们本来只是一堆具体条件下的观察，被抽掉了条件，就变成了迷信。

特定场景有特定的做法。不要信"哪个语言快"，只信自己验出来的数。
